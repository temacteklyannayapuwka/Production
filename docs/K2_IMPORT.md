# Миграция Joomla K2 в StavPlus

Импортёр предназначен только для локальной проверки и тестового контура
`new.stavplus.ru`. На основном `stavplus.ru` его не запускают до завершения
ручной сверки результатов.

## Что переносится

Первый этап переносит:

- категории из `<prefix>k2_categories`;
- теги и связи из `<prefix>k2_tags` и `<prefix>k2_tags_xref`;
- новости из `<prefix>k2_items`;
- главное изображение K2 по `md5("Image" + item_id)`;
- локальные ссылки `src` и `href`, начинающиеся с `/media/k2/` или `/images/`.

Галереи, attachments, extra fields, авторы, комментарии и рейтинги в первый этап
не входят. `NewsGallery` в StavPlus уже существует, но для него сначала нужно
исследовать реальные K2 gallery-данные и согласовать отдельное преобразование.

Legacy ID хранится непосредственно в nullable unique-полях `legacy_k2_id` у
`News`, `Category` и `Tag`. Это проще и надёжнее отдельной mapping-таблицы для
единственного источника K2: база обеспечивает уникальность, а повторный запуск
находит запись по стабильному ID. Существующие редакционные записи с `NULL` не
затрагиваются; совпавшие по точному имени категории и теги аккуратно получают
legacy ID вместо создания дубля.

Импорт новых `News` и обновление существующих выполняются без вызова
`News.save()`. Это намеренно: текущий `save()` корректирует даты и статусы и
конвертирует изображения, что исказило бы исходные значения K2. Каждая новость
записывается в своей транзакции, поэтому ошибка одной записи не откатывает весь
многочасовой импорт.

## Что нужно предоставить

Обязательно:

- read-only доступ к таблицам `<prefix>k2_items`, `<prefix>k2_categories`,
  `<prefix>k2_tags`, `<prefix>k2_tags_xref` в MySQL/MariaDB;
- локальную доступную копию Joomla-каталога `media/k2/`;
- точный префикс таблиц, charset и IANA timezone старого Joomla;
- список ID исключаемых категорий.

Желательно предоставить каталог `images/`. Для второго этапа понадобятся
`<prefix>k2_attachments`, `<prefix>k2_extra_fields`,
`<prefix>k2_extra_fields_groups`, `media/k2/galleries/` и
`media/k2/attachments/`.

До первого реального запуска нужно отдельно посмотреть фактические имена и
расширения файлов в `media/k2/items/src/` и `media/k2/items/cache/`. Импортёр уже
поддерживает `jpg`, `jpeg`, `png`, `webp` и порядок original → XL → L → Generic
→ остальные найденные варианты, но отчёт должен подтвердить соответствие
реальному архиву.

## Окружение

Установите отдельный набор зависимостей импортёра:

```bash
pip install -r requirements-k2.txt
```

Задайте переменные вне Git, например в локальном `.env` или настройках процесса:

```dotenv
K2_DB_HOST=127.0.0.1
K2_DB_PORT=3306
K2_DB_NAME=legacy_joomla
K2_DB_USER=legacy_reader
K2_DB_PASSWORD=replace-locally
K2_DB_PREFIX=jos_
K2_DB_CHARSET=utf8mb4
K2_TIME_ZONE=Europe/Moscow
K2_MEDIA_ROOT=/absolute/path/to/joomla-root
K2_REPORT_DIR=/absolute/path/to/k2-import-reports
```

Пользователь `K2_DB_USER` должен иметь только `SELECT` на legacy-базу. Импортёр
дополнительно переводит сессию в read-only режим и выполняет только `SELECT` и
`SHOW`. Пароль не выводится в отчёт; если драйвер вернёт его в тексте ошибки,
команда заменит значение на `[REDACTED]`.

`K2_TIME_ZONE` обязателен: naive timestamps Joomla интерпретируются именно в
этой зоне, а не в зоне машины запуска. Нулевые MySQL-даты считаются
отсутствующими. Charset по умолчанию — `utf8mb4`, но его нужно сверить с legacy
БД.

## Безопасный порядок запуска

1. Убедитесь, что окружение указывает на `new.stavplus.ru` или локальную БД, а не
   на основной `stavplus.ru`.
2. Создайте полную восстанавливаемую резервную копию целевой БД и целевого
   `MEDIA_ROOT` средствами хостинга/СУБД. Проверьте, что backup читается.
3. Установите код и примените миграции только в тестовом контуре:

   ```bash
   python manage.py migrate
   ```

4. Запустите анализ без изменений:

   ```bash
   python manage.py import_k2 --dry-run
   ```

   Флаг можно не писать: отсутствие `--apply` всегда означает dry-run. В этом
   режиме Django records и media не меняются; создаются только JSON-отчёт и
   sanitized error log.

5. Сверьте counts, статусы, даты, пропущенные связи, slug collisions, найденные
   и отсутствующие изображения. При необходимости исключите категории:

   ```bash
   python manage.py import_k2 --dry-run \
     --exclude-category 17 --exclude-category 42
   ```

6. После успешной сверки импортируйте первые 10 записей:

   ```bash
   python manage.py import_k2 --limit 10 --apply
   ```

7. Вручную проверьте эти 10 новостей в админке и на тестовом сайте: URL, HTML,
   timezone, статусы, категорию, теги, главное и inline-изображения.
8. Повторите ту же команду с `--limit 10 --apply`. В отчёте должны быть updates,
   а количество `News`, категорий, тегов и файлов не должно удвоиться.
9. Только после этого выполните полный импорт:

   ```bash
   python manage.py import_k2 --apply
   ```

Пути и timezone можно явно передать параметрами:

```bash
python manage.py import_k2 --dry-run \
  --legacy-root /absolute/path/to/joomla-root \
  --legacy-timezone Europe/Moscow \
  --report-dir /absolute/path/to/reports
```

## Продолжение после сбоя

Записи читаются по возрастанию K2 ID. Отчёт показывает последний успешно
обработанный ID. Resume включителен и безопасен благодаря `legacy_k2_id`:

```bash
python manage.py import_k2 --resume-from-id 12345 --apply
```

Одна ошибочная новость фиксируется в error log и не останавливает следующие.
После исправления причины можно повторить запуск с её ID. Уже импортированные
объекты обновятся, а content-addressed media повторно не скопируются.

## Отчёты и восстановление

По умолчанию файлы создаются в `var/k2-import/`:

- `k2-import-<mode>-<timestamp>.json` — counts, проблемы, ошибки, выбранная
  featured-новость и последний успешный ID;
- `k2-import-<mode>-<timestamp>.errors.log` — краткий sanitized список ошибок.

Отчёты не коммитятся. Если `--apply` дал неприемлемый результат, надёжный
rollback — восстановить целевую БД и `MEDIA_ROOT` из проверенного backup. Не
следует массово удалять строки только по `legacy_k2_id`: импортёр может безопасно
привязать существующую категорию или тег с тем же именем. Автоматический
destructive rollback намеренно не предусмотрен.

После полного запуска сохраните отчёт вне рабочей папки приложения и сравните
число исходных не-trash записей с суммой импортированных, обновлённых и
пропущенных записей.
